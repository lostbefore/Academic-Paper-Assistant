## 12.3 阶段一：立项与 v1 原型（2026-03-20）

### 12.3.1 起点

最初的动机很具体：大模型能写论文，但写出来的东西**不能查**——参考文献查无此文，数据凭空出现，读者无法判断哪句话有出处。因此 v1 的目标不是「生成得更快」，而是「让生成过程有据可查」。

技术选型在当天完成：Python + FastAPI 做后端（异步适合流式与并发检索）、React + TypeScript 做前端、Semantic Scholar 与 arXiv 做文献源、python-docx 做导出。

|---|---|---|
| 13:35 | `aee700e` | 初始提交：CLI 插件、研究代理、写作代理、文献检索、格式化、图片检索、DOCX 生成、React 四页面 |
| 13:46 | `22985ca` | README 拆分为中英双语，明确项目定位与免责声明 |
| 14:03 | `6e0ca65` | 增加 Dockerfile、compose 与部署文档，尝试容器化 |

| 15:32 | `f855511` | 修复 Semantic Scholar 429 限流：请求间加延迟并降级到 arXiv |

这 6 次提交体现了一个真实的开发节奏：**先跑通 → 再补文档 → 再想部署 → 再处理限流**。429 那次修复尤其典型：外部服务的限流不是设计问题，而是上线后才会暴露的运行问题。

### 12.3.3 v1 已具备的能力

- 多源文献检索（Semantic Scholar + arXiv），带 429 退避；
- 研究代理：围绕选题生成研究问题与背景；
- 写作代理：按章节生成摘要、引言、综述、方法、结果、讨论、结论；
- 四种引用格式的格式化函数；
- DOCX 导出（含中文排版设置）；
- 一套学术写作知识库（`knowledge/`）。

### 12.3.4 v1 的结构性缺陷

v1 能跑，但无法交付给真实用户。使用中暴露出的问题按严重程度排列：

| 编号 | 问题 | 后果 |
|---|---|---|
| P1 | 论文只存在进程内 `dict` | 服务一重启，所有稿子消失 |
| P2 | 没有账户体系 | 不能放到公网，任何人都能读别人的论文 |
| P3 | 生成是「一次性后台任务」 | 用户看不到进度，失败也没有提示 |
| P4 | 章节不能单独修改 | 改一处只能整篇重来，浪费 token |
| P5 | PDF 导出依赖 `docx2pdf`（需要 Word） | Linux 服务器上直接不可用 |
| P6 | 前端类型检查不通过 | 构建不出可部署的静态资源 |
| P7 | 依赖清单与实际代码不一致 | 换一台机器装不起来 |

这七条构成了 v2 的需求来源。换句话说，**v2 的每一条设计决策都能对应到 v1 的一个具体失败**。

## 12.4 阶段二：架构重构（2026-11-16 13:50–14:30）

### 12.4.1 先定边界，再写代码

重构前先确定了五条约束（详见第 02 章 2.1）：单进程可运行、状态可恢复、失败要隔离、边界要清晰、不隐藏成本。这五条直接决定了后面的技术选择：

- 不引入 Redis/Celery → 任务用 `asyncio.Task`，状态落 SQLite；
- 不引入 ORM → 表少，参数化 SQL 更直接；
- 不依赖 LibreOffice → 用 `reportlab` 直接生成 PDF。

### 12.4.2 后端搭建顺序

| 顺序 | 模块 | 为什么先做它 |
|---|---|---|
| 1 | `config.py` | 所有模块都依赖配置，先定环境变量与路径解析 |
| 2 | `db.py` | 持久化是 v1 最大的缺口，先定表结构 |
| 3 | `security.py` / `deps.py` | 有账户才敢放公网 |
| 4 | `llm.py` | 生成链路的地基，必须先能稳定调用模型 |
| 5 | `literature.py` | 引用可溯源的前提 |
| 6 | `prompts.py` / `citations.py` | 提示词与引用格式，决定成稿质量 |
| 7 | `pipeline.py` | 把上面几块串成六阶段流水线 |
| 8 | `export.py` | 交付形态 |
| 9 | `routers/*` + `main.py` | 最后暴露 HTTP 接口与静态资源 |

这个顺序不是随意的：**越靠底层、越被依赖的模块越早写**，因此每次写完都能立刻被后面的模块验证。

### 12.4.3 关键实现片段

**流水线的进度映射**（`pipeline.py`）：检索 2→12、提纲 15→24、写作 26→90、摘要 92、文献表 96→100。写作阶段按 `index / total` 分摊区间，保证进度条单调递增。

**逐节落库**：每写完一节立即 `UPDATE papers SET sections_json=?`，再写一条事件。这样即使第五节失败，前四节仍在，用户能看到半成品并重试。

**语言相关的 token 预算**（`_max_tokens`）：中文按 `words × 0.55` 估算，英文按 `words × 2.0`。这个系数是实测出来的——见 12.6 的 BUG-04。

## 12.5 阶段三：前端重建（2026-11-16 14:27–14:40）

v1 的前端有四个页面，但没有登录、没有进度、没有编辑。v2 的做法是：

1. **先加认证层**：`AuthContext` + axios 拦截器 + 路由守卫，任何页面在未登录时跳转 `/login`；
2. **重写论文查看器**：从「只读展示」改为「三视图 + 编辑 + 重写 + 导出 + 日志」；
3. **新增两个页面**：文献检索（脱离生成独立使用）、设置（模型自检与运行环境）；
4. **补类型**：新增 `vite-env.d.ts`，把 `Paper`、`ProgressEvent` 等类型收敛到 `types/index.ts`。

其中最容易出错的是 **SSE 的消费方式**：`EventSource` 不能带 `Authorization` 头，所以改用 `fetch` + `ReadableStream` 手写帧解析，并在后端额外支持 `?token=` 作为兜底。

## 12.6 阶段四：联调与缺陷修复（2026-11-16 14:20–14:55）

这一阶段是整个开发过程中信息量最大的部分。下面每个缺陷都是**先出现、再定位、后修复、最后验证**，不是事后补写的清单。

### 缺陷 1：创建论文直接 500

- **现象**：`POST /api/papers` 返回 `{"detail":"Internal server error"}`；
- **定位**：日志里是 `RuntimeError: no running event loop`。路由函数写成了同步 `def`，FastAPI 把它放到线程池执行，线程里没有事件循环，`asyncio.create_task` 失败；
- **修复**：改成 `async def`；
- **验证**：创建返回 202，SSE 能持续收到事件。

### 缺陷 2：英文作者姓名颠倒

- **现象**：APA 输出 `Ashish, V.`，IEEE 输出 `V. Ashish`；
- **定位**：`_split_name` 把 `parts[:-1]` 当姓氏，实际应取最后一段；
- **修复**：取 `parts[-1]` 为姓，并支持 `Family, Given` 形式；
- **验证**：6 条引用格式用例全部通过。

### 缺陷 3：中文论文长度 1.9 倍超标

- **现象**：目标 2500 字，实际生成 4971 字；
- **定位**：三个原因叠加——token 预算按英文习惯估算、提示词写「800 words」而非「800 汉字」、模型照抄提纲示例字数未重标定；
- **修复**：分语言预算 + 汉字区间提示 + 提纲字数按目标重标定；
- **验证**：目标 2800 字产出约 3400 字（1.21 倍）。

### 缺陷 4：前端构建不通过

- **现象**：`tsc` 报三类错误（未使用的 React 导入、`Paper` 上不存在 `citation_style`、`import.meta.env` 无类型）；
- **修复**：删除无用导入、改用 `paper.request?.citation_style`、新增类型声明文件；
- **验证**：构建成功，产物 gzip 139 KB。

### 缺陷 5：线上服务反复重启

- **现象**：`apa.service` 处于 `activating (auto-restart)`；
- **定位**：安装脚本 `chmod 600 .env` 但属主仍是 root，服务以 `apa` 用户运行，读取失败；
- **修复**：先 `chown apa:apa` 再 `chmod 600`；
- **验证**：服务 `active (running)`，健康检查返回 ok。

### 缺陷 6：外网 80 端口不可达

- **现象**：服务器本机访问正常，外部超时；
- **定位**：`ufw` 未启用、`iptables` 默认 ACCEPT，排除主机防火墙；判断为云厂商安全组未放行；
- **修复**：控制台添加入站规则 `TCP:80`；
- **验证**：外网 `GET /api/health` 返回 200，静态资源与登录接口均正常。

|---|---|---|---|
| BUG-01 | 第一次调用创建接口 | 阻塞全流程 | 分钟级 |

## 12.10 复盘

### 做对了什么

1. **先定失败模式再定架构**：v2 的每个模块都对应 v1 的一个具体缺陷，没有为了「看起来专业」而引入多余组件；
2. **状态落库**：正因为进度、章节、事件都写进数据库，才敢把任务放在进程内，也才能在重启后自愈；
3. **用测试抓缺陷**：BUG-02 是靠断言发现的，不是靠肉眼；
4. **部署脚本化**：`.env` 权限这种低级错误只会在第一次部署时踩一次，脚本固化后不会重复。

### 遗留问题

| 问题 | 现状 | 计划 |
|---|---|---|
| 修改密码 | 只能脚本重置 | 增加改密接口 |
| 参考文献真伪反查 | 依赖检索元数据 | 接入 Crossref 校验 DOI 存在性 |
| PDF 中文字体 | CID 字体，个别阅读器提示缺失 | 改为内嵌 Noto CJK 子集 |
| 并发压测 | 仅验证 2 并发 | 补 10 并发以上的压测 |
| 本地迭代期（3–6 月） | 未纳入版本控制，无提交记录 | 以设计文档、源码与运行记录为证；如需补强，可并入当时留存的本地稿 |

## 12.11 小结

这条开发路径可以概括为一句话：**先把问题暴露出来，再让每个设计决策都对上一个具体问题**。

v1 用一天时间证明「技术上可行」，v2 用一天时间把它变成「可以交付」：有账户、有持久化、有进度、能编辑、能导出、能部署、能测试、能追溯。中间的差距不是代码量，而是**工程约束**——每加一条约束（不引入 Redis、不依赖 Office、单进程运行），都要用另一种方式把问题解决掉，而这些取舍正是本记录想呈现的部分。
