## 3.1 选型与总体设计

系统采用 SQLite（WAL 模式），单文件 `data/apa.db`。选择理由：

- 目标部署环境是单台 1.7 GB 内存的云主机，引入独立数据库服务会额外占用 200 MB 以上；
- 业务写入频率低（一个用户一天内几次生成），读多写少，WAL 足以支撑；
- 备份即复制文件，便于教学场景中的迁移与归档。

表结构遵循两条约定：

1. **半结构化字段统一用 JSON 文本**：提纲、章节、参考文献、请求参数的结构会随提示词迭代而变化，用 JSON 列避免频繁改表；
2. **所有时间字段为 UTC ISO-8601 字符串**（`2026-11-16T06:34:57Z`），便于排序与跨时区显示。

## 3.2 实体关系

```
users 1 ──── n papers          （删除用户级联删除论文）
papers 1 ──── n events         （事件按 paper_id + 自增 id 顺序读取）
literature_cache 独立          （按 query hash 命中）
```

外键 `papers.user_id → users.id ON DELETE CASCADE`，连接时执行 `PRAGMA foreign_keys = ON` 保证生效。

## 3.3 表结构

### 3.3.1 users —— 账户

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | TEXT | PK | `uuid4().hex` |
| email | TEXT | NOT NULL UNIQUE | 统一小写存储 |
| name | TEXT | NOT NULL DEFAULT '' | 显示名，同时用作论文署名 |
| password_hash | TEXT | NOT NULL | bcrypt，`$2b$12$...` |
| role | TEXT | NOT NULL DEFAULT 'user' | `user` / `admin` |
| created_at | TEXT | NOT NULL | 注册时间 |
| last_login_at | TEXT | NULL | 最近登录时间 |

索引：`UNIQUE(email)` 由约束自动创建。

### 3.3.2 papers —— 论文（核心表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | TEXT | PK | `p_` + 12 位 hex |
| user_id | TEXT | NOT NULL, FK | 归属用户 |
| title | TEXT | NOT NULL | 展示标题，可在生成后被模型改写 |
| status | TEXT | NOT NULL | `queued/running/completed/failed/cancelled` |
| stage | TEXT | NOT NULL | `researching/outlining/writing/abstract/references/...` |
| progress | INTEGER | NOT NULL | 0–100，供前端进度条 |
| request_json | TEXT | NOT NULL | 生成参数快照：标题、领域、关键词、长度、字数、引用格式、语言、补充要求 |
| outline_json | TEXT | NOT NULL | 提纲：`{title, research_questions[], method, sections[{key,title,goal,words}]}` |
| sections_json | TEXT | NOT NULL | 章节正文：`{abstract, introduction, ..., references}` |
| refs_json | TEXT | NOT NULL | 检索到的文献元数据数组 |
| meta_json | TEXT | NOT NULL | `word_count / tokens_in / tokens_out / reference_count / model / finished_at` |
| error | TEXT | NOT NULL | 失败原因（面向用户可读） |
| created_at / updated_at | TEXT | NOT NULL | 创建、最后变更 |
| finished_at | TEXT | NULL | 完成时间 |

索引：
- `idx_papers_user(user_id, created_at DESC)` —— 列表页按人按时间倒序；
- `idx_papers_status(status)` —— 启动自检扫描未完成任务。

**为什么把章节放在一个 JSON 列而不是单独的 sections 表？**
章节固定为 6+2 个键、总是整体读取、无需按节查询；单列 JSON 让「读一篇论文」只有一次查询，也避免生成过程中多行更新的锁竞争。章节级编辑直接改写整个 JSON（体积 < 30 KB），成本可忽略。

### 3.3.3 events —— 过程事件

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK AUTOINCREMENT | 单调递增，SSE 断点续传的依据 |
| paper_id | TEXT | 所属论文 |
| ts | TEXT | 事件时间 |
| stage | TEXT | 阶段：`researching/writing/...` |
| level | TEXT | `info/warning/error` |
| message | TEXT | 人类可读描述 |
| data_json | TEXT | 结构化附加信息（章节 key、字数、文献数） |

索引 `idx_events_paper(paper_id, id)` 支撑 `id > ?` 的增量查询。

写入时做**事件裁剪**：每篇论文只保留最近 800 条，避免长时间运行后表膨胀：

```sql
DELETE FROM events
WHERE paper_id = ?
  AND id < (SELECT MAX(id) - 800 FROM events WHERE paper_id = ?);
```

### 3.3.4 literature_cache —— 检索缓存

| 字段 | 类型 | 说明 |
|---|---|---|
| key | TEXT PK | query + limit + year + sources 的 SHA-256 |
| payload | TEXT | 合并后的文献数组 |
| created_at | TEXT | 写入时间 |
| expires_at | TEXT | 过期时间（默认 72 小时） |

缓存的作用不是省流量，而是**保证同一选题在短时间内重复生成时引用一致**，便于学生对照与教师复核。

## 3.5 状态机

```
        ┌──────────┐  POST /papers
        │  queued  │◄───────────────┐
        └────┬─────┘                │ retry
             │ 任务启动              │
        ┌────▼─────┐                │
        │ running  │────────────────┘
        └────┬─────┘
     ┌───────┼─────────┬───────────┐
     │       │         │           │
┌────▼───┐ ┌─▼──────┐ ┌▼─────────┐ │
│completed│ │ failed │ │cancelled │ │
└────────┘ └────────┘ └──────────┘ │
     ▲                              │
     └────────── 编辑/重写 ◄────────┘
```

规则：

- 只有 `completed` 才允许导出；
- `running/queued` 时禁止重写单节（避免与流水线写冲突）；
- 服务重启时，所有 `queued/running` 被改写为 `failed` 并附原因「被重启中断，可重试」。

## 3.6 容量与维护

| 项目 | 估算 |
|---|---|
| 单篇论文 JSON 体积 | 15–40 KB（6000 字规模） |
| 单篇事件体积 | 20–40 KB（裁剪后上限 800 条） |
| 1000 篇论文的库大小 | 约 60–90 MB |
| 导出文件 | DOCX 40 KB / PDF 15 KB（按篇存储，可随时重生成） |

维护动作：

```bash
sqlite3 data/apa.db "VACUUM;"                    # 压缩空间
sqlite3 data/apa.db ".backup data/backup.db"      # 在线备份
```
