## 5.1 为什么不用「一次调用生成全文」

最初的设计是构造一个长提示词，让模型一次输出整篇 Markdown，再按标题切分。实测遇到四个问题：

1. 正文超过约 3000 字后，模型开始丢失前文约束，后几节明显模板化；
2. 一次调用动辄 3–5 分钟，期间没有任何可用输出，用户只能等待；
3. 任何一侧超时或截断，整篇作废，token 全部浪费；
4. 无法针对某一节重写，只能整篇重来。

因此改为**六阶段流水线**，每节独立调用、独立落库、独立重试。

## 5.2 阶段划分

| 阶段 | 代码方法 | 进度区间 | 产出 | 失败影响 |
|---|---|---|---|---|
| 检索 | `_research` | 2 → 12 | 文献数组 `refs_json` | 不致命，降级为「无引用」 |
| 提纲 | `_outline` | 15 → 24 | `outline_json` | 解析失败则用默认提纲 |
| 写作 | `_write_sections` | 26 → 90 | `sections_json`（逐节累积） | 致命，保留已完成章节 |
| 摘要 | `_abstract` | 92 | `sections.abstract` | 失败则用提纲摘要兜底 |
| 文献表 | `_finalise` | 96 → 100 | `sections.references` | 不会失败（本地格式化） |
| 完成 | — | 100 | `status=completed` | — |

进度按阶段线性插值，写作阶段按 `index / total` 分配 26–90 的区间，因此前端进度条是**单调递增**的，不会回退。

## 5.3 提纲生成与归一化

模型被要求输出严格 JSON：

```json
{
  "title": "polished academic title",
  "abstract_brief": "2-3 sentence summary",
  "research_questions": ["RQ1", "RQ2"],
  "theoretical_framework": "one sentence",
  "method": "research design",
  "sections": [
    {"key": "introduction", "title": "...", "goal": "...", "words": 800}
  ]
}
```

程序侧做三步归一化（`_normalise_outline`）：

1. **补齐**：六个 key（introduction / literature_review / methodology / results / discussion / conclusion）必须齐全，缺失的用默认值填充，顺序固定；
2. **纠偏**：`words` 缺失或为 0 时按默认比例回填；
3. **重标定**：把模型给出的字数按比例缩放到用户的目标字数——模型经常照抄提示词里的示例字数，导致总字数偏离 2 倍以上。

> 实测：未重标定时，目标 2500 字的论文实际产出 4971 字；加入重标定后，目标 2800 字产出约 3400 字（偏差 21%），目标 2200 字产出 2686 字（偏差 22%）。

## 5.4 分节写作

### 5.4.1 提示词结构

每条章节请求由三部分组成：

```
[system]  角色设定 + 硬约束（禁止编造数据/文献、只引用给定编号、学术语体、不输出标题）
[user]    论文标题 / 研究问题 / 理论框架 / 方法
          本节目标 + 长度区间
          已完成章节的摘要（每节取前 600 字）
          编号文献块（作者、年份、标题、期刊、摘要前 420 字）
          格式与引用要求
```

**为什么只传前节摘要而不是全文？**
六节全文约 6000 字，全部塞进上下文会让每次调用多消耗 4–6k token，且对连贯性的边际收益很低；截取每节前 600 字足以让模型知道「前面写了什么」。

### 5.4.2 长度控制

长度预算按语言分别计算（`_max_tokens`）：

```python
if language == "zh":
    return max(300, min(4000, int(words * 0.55) + 120))
return max(500, min(6000, int(words * 2.0) + 200))
```

依据来自实测：DeepSeek 系列分词器对中文约 5.5 字符/token，对英文约 0.5 词/token。若按英文习惯给中文设 `words*2`，上限会放大到实际需要的 3–4 倍，模型便会写超。

提示词中同时给出区间：「约 600 汉字，不少于 480、不多于 720」，约束模型主动收敛。

### 5.4.3 单节字数分配

默认比例（`SECTION_SHARE`）：

| 章节 | 占比 | 6000 字论文 |
|---|---:|---:|
| 引言 | 13% | 780 |
| 文献综述 | 24% | 1440 |
| 研究方法 | 17% | 1020 |
| 研究结果 | 19% | 1140 |
| 讨论 | 17% | 1020 |
| 结论 | 10% | 600 |

该比例来自人文社科类论文的常见结构；提纲阶段允许模型在此基础上微调，最终以重标定后的值为准。

## 5.5 引用一致性

引用是本系统最关键的约束，分三层保证：

1. **编号先行**：文献在提示词中以 `[1] … [n]` 编号出现，模型被要求只能使用这些编号；
2. **本地生成文献表**：`sections.references` 由 `citations.build_reference_list()` 根据检索元数据生成，**不经过模型**，因此不可能出现不存在的条目；
3. **失败降级**：若检索为空，提示词明确写「no external references were retrieved」，最终文献表写入说明性文字，而不是让模型编造。

不同格式的正文引用方式（`citation_examples`）：

- IEEE / GB-T 7714：`[1]`、`[2]`，与文献表编号对应；
- APA / MLA：`(Smith, 2023)` 形式，要求作者与年份必须出现在文献表中。

## 5.6 事件与状态

每个阶段写事件（`log_event`），字段：

| 字段 | 例 |
|---|---|
| stage | `writing` |
| message | `Finished 文献综述 (677 words)` |
| level | `info` / `warning` / `error` |
| data | `{"section": "literature_review", "words": 677}` |
| progress | 同步写入 `papers.progress` |

事件的三个用途：前端实时展示、失败后排查、以及作为「AI 使用过程留痕」的证据。

## 5.7 失败与恢复

| 场景 | 处理 |
|---|---|
| 模型未配置 | 创建论文时直接 503，不进入队列 |
| 单节返回空 | 抛 `LLMError`，整篇标记失败，已写章节保留 |
| 模型超时 / 429 | `LLMClient` 指数退避重试 3 次，仍失败则整篇失败 |
| 检索全部失败 | 记 warning，继续生成（无引用模式） |
| 用户取消 | `job_manager.cancel()` 置状态并 `task.cancel()`，捕获 `CancelledError` 后写 `cancelled` 事件 |
| 进程崩溃/重启 | 启动时把 `queued/running` 改为 `failed`，提示可重试 |
| 重试 | 清空事件、重置进度、重新入队；旧章节会在第一节写完后被覆盖 |

## 5.8 并发控制

```python
class JobManager:
    _tasks: dict[str, asyncio.Task]
    _semaphore: asyncio.Semaphore(MAX_CONCURRENT_JOBS)  # 默认 2
```

- 同一篇论文重复点击生成会被 `is_running()` 拦截；
- 超出并发的任务在信号量上排队，状态保持 `queued`；
- 进程退出时 `shutdown()` 取消所有任务，避免僵尸协程。

## 5.10 已知局限

1. 「研究结果」章节是对研究设计的推演式描述，**不产生真实实验数据**——这是设计边界，不是缺陷；
2. 中文分词与字数统计按「汉字数 + 英文词数」计算，与 Word 的「字数」口径略有差异（标点、数字处理不同）；
3. 改写单节时只参考其他章节前 600 字，极端情况下可能与远处章节的术语不一致。
